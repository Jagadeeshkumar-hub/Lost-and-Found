📐 High-Precision Multi-Factor Recommendation Algorithm

The recommendation engine eliminates false matches by enforcing strict multi-factor qualification: (1) Category Consistency (25 pts: mandatory prerequisite), (2) Keyword & Title Similarity (up to 40 pts: tokenized subject and brand overlap; requires at least 1 keyword match to qualify), (3) Location Proximity (20 pts: exact campus zone or adjacent building), and (4) Date Order & Proximity (15 pts: Found Date ≥ Lost Date within 21 days; negative time intervals are strictly disqualified).

MySQL 8.0 Database Scripts & Architecture Reference

Complete overview of relational schema, constraints, SQL scripts, views, and execution procedures.

🗂️ Relational Schema Structure (campus_lost_found)

5 Normalized Relational Tables
TABLE: Users

Campus Members

Stores students, faculty, staff, and security personnel who report or claim items.

Keys: PK (user_id), UNIQUE (student_or_staff_id, email)
Constraints: CHECK (user_type IN ('STUDENT', 'FACULTY', 'STAFF', 'SECURITY'))
TABLE: Locations

Campus Zones

Tracks buildings, floors, and specific rooms where items are lost or discovered.

Keys: PK (location_id), UNIQUE (location_name)
Constraints: CHECK (zone_type IN ('ACADEMIC', 'LIBRARY', 'SPORTS', 'CANTEEN', 'HOSTEL', 'ADMIN', 'LABORATORY'))
TABLE: Lost_Items

Reported Losses

Records lost item descriptions, reporter reference, last-seen location, and status.

Keys: PK (lost_id), FK (user_id → Users), FK (location_id → Locations)
Constraints: CHECK (category IN (...)), CHECK (status IN ('REPORTED', 'POSSIBLE_MATCH', 'RETURNED', 'CLOSED'))
TABLE: Found_Items

Recovered Belongings

Tracks found items, safe custody desk, finder reference, and claim lifecycle status.

Keys: PK (found_id), FK (finder_id → Users), FK (location_id → Locations)
Constraints: CHECK (status IN ('UNCLAIMED', 'CLAIM_PENDING', 'CLAIMED', 'DISPOSED'))
TABLE: Claims

Verification Claims

Associative entity managing ownership claims, verification evidence, and security resolution.

Keys: PK (claim_id), FK (found_id → Found_Items), FK (claimant_id → Users), FK (lost_id → Lost_Items)
Constraints: CHECK (claim_status IN ('PENDING', 'VERIFIED', 'APPROVED', 'REJECTED'))

💻 How to Run in MySQL Workbench 8.0

Viva & Lab Evaluation Instructions
  1. Open MySQL Workbench and connect to your local MySQL 8.0 server instance (e.g., localhost:3306 as root).
  2. Go to File > Open SQL Script... and navigate to the project's sql/ folder.
  3. Open and execute 01_create_database.sql (click the lightning bolt icon ⚡) to build the database and tables.
  4. Open and execute 02_insert_sample_data.sql to load the sample records.
  5. Run 03_basic_queries.sql to test joins, filters, and aggregations.
  6. Run 04_matching_queries.sql to demonstrate the multi-factor candidate matching queries.
  7. Run 05_views_and_reports.sql to create the views (vw_possible_matches, etc.).
  8. Run 06_claim_processing.sql to demonstrate transaction commits and rollbacks.
